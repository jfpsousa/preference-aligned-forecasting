## 1. Quick start

```bash
git clone https://github.com/jfpsousa/preference-aligned-forecasting.git
cd preference-aligned-forecasting
python3 -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt --extra-index-url https://download.pytorch.org/whl/cpu

./reproduce.sh --smoke     # optional, ~1 minute: whole pipeline at toy scale
./reproduce.sh             # full reproduction
```

`reproduce.sh` runs every stage in order without intervention and writes all
tables to `outputs/tables/`; `outputs/tables/SUMMARY.md` collects them in one
readable file. The run log is `outputs/logs/reproduce.log`.

The script is resumable: each experiment job writes its own result file, and
re-running `./reproduce.sh` skips jobs that already finished. Delete `outputs/`
to recompute everything.

`--smoke` runs the identical pipeline (all datasets, stages and tables) with a
tiny network and very few training steps. Its numbers are meaningless; it only
checks the installation.

## 2. Hardware, software

* **Hardware.** CPU only; no GPU is needed or used. Measured on a 16-core x86_64
  Linux workstation with 93 GB RAM: (stage
  breakdown below). Peak memory is below 8 GB. Disk: ~1.5 GB (raw data ~0.5 GB,
  processed data and outputs ~1 GB).
* **Parallelism.** Jobs run in parallel, `parallel.workers` (8) processes with
  `parallel.threads_per_worker` (2) PyTorch threads each — set for 16 cores in
  `configs/paper.yaml`. On a machine with fewer cores, reduce `workers`; runtime
  scales roughly inversely with total cores.
* **Software.** Python ≥ 3.11 (tested with CPython 3.14.6). Pinned direct
  dependencies in `requirements.txt`; the exact environment used, including
  transitive dependencies, in `requirements-lock.txt`.

| Stage | What it does |
|---|---|
| 1 data | download, checksum, preprocess 6 datasets |
| 2 main | 6 datasets × 5 seeds, all methods |
| 3 ablation | 3 synthetic datasets × 5 seeds |
| 4 sweep | M5 × 5 seeds × 4 cost ratios |
| 5 beta | 3 real datasets × 5 seeds × 6 values of β |
| 6 tables | statistics and tables |

Yahoo Finance revises adjusted prices retroactively (dividends, splits), so a
fresh download would not reproduce the same data. The package therefore ships the
exact snapshot it uses. `scripts/refresh_yahoo_snapshot.py` shows how it was
produced.

If a downloaded file does not match its recorded checksum, the run stops with an
error rather than silently using different data.

## 5. Workflow

```
reproduce.sh
├─ pytest tests/                          unit tests (metric, splits, T-DPO loss)
├─ scripts/prepare_data.py                stage 1  data/raw -> data/processed/*.npz
├─ scripts/run_jobs.py --stage main       stage 2  outputs/runs/*/seed*/main.json
├─ scripts/run_jobs.py --stage ablation   stage 3  outputs/runs/synthetic_*/seed*/ablation.json
├─ scripts/run_jobs.py --stage sweep      stage 4  outputs/runs/m5/seed*/sweep.json
├─ scripts/run_jobs.py --stage beta       stage 5  outputs/runs/{m5,uci_energy,yahoo_etf}/seed*/beta.json
└─ scripts/make_tables.py                 stage 6  outputs/tables/
```

**Stage 2 (main).** For each dataset and seed:
1. *Naive*: persistence forecast (last observation).
2. *MSE baseline*: Transformer trained on squared error. It is also the T-DPO
   reference policy π_ref.
3. *PatchTST*, *Informer* (Table 2 only): trained on squared error.
4. *Asymmetric Loss*: the same Transformer trained on the fixed-ratio
   asymmetric loss.
5. *Oracle* (Table 2 only): the same Transformer trained on the exact
   evaluation cost.
6. *Temporal-DPO*:
   * π_ref draws K = 8 candidate trajectories per training context.
   * The constitutional principles P1–P4 score each candidate. The best and
     worst form a preference pair (5,000 pairs).
   * A copy of π_ref is fine-tuned with the temporal DPO loss
     (Algorithm 1, Eq. 17; β = 0.1, γ = 0.95).

All methods are then scored on the same held-out test windows.

**Stage 3 (ablation).** This stage reuses π_ref and the preference pairs from
stage 2:
* *γ sweep*: γ ∈ {0.75, …, 0.99, 1.0}. γ = 1 is standard sequence-level DPO.
* *Sample efficiency*: n ∈ {500, …, 10,000} preference pairs for T-DPO, and the
  same number of labelled windows for Asymmetric Loss.
* *Principles*: leave-one-out over P1–P4, plus "none", which ranks candidates by
  squared error alone.
* *Reference policy*: a randomly initialised reference instead of the
  MSE-pretrained one.

**Stage 4 (sweep).** For the retail cost ratio α ∈ {2, 3, 5, 10} on M5, it
retrains Asymmetric Loss and regenerates the pairs (P3 uses α). It then
fine-tunes T-DPO and evaluates every model under cost ratio α.

**Stage 5 (β).** On M5, UCI Energy and Yahoo, π_ref and the 5,000 pairs from
stage 2 are fine-tuned with β ∈ {0.01, 0.05, 0.1, 0.5, 1.0, 2.0}. Only β
changes; the fine-tuning seed is the same for every β. Each model is scored on
the validation windows (non-overlapping H-step blocks inside the validation
period) and on the test windows.
* *Selection (Section 7.1)*: β ∈ {0.01, 0.05, 0.1, 0.5, 1.0} with the highest
  validation decision accuracy; ties go to lower validation cost, then smaller β.
  The selected β is reported per dataset and seed. The main experiments use the
  configured β = 0.1 throughout, so `beta_selection.csv` shows whether validation
  agrees with it.
* *Ablation (Section 7.4)*: test-set results for β ∈ {0.1, 0.5, 1.0, 2.0}.

**Splits.** Splits are chronological, as in Appendix B.2 of the paper:

| Data | Train / validation / test | Horizon H |
|---|---|---|
| M5 | 80/10/10 | 28 days |
| UCI | 70/10/20 | 24 hours |
| Yahoo | 2018–2022 / Jan–Jun 2023 / Jul–Dec 2023 | 5 days |
| Synthetic | 70/10/20 | as the matching real domain |

Training windows have all their targets inside the training period. Test windows
are non-overlapping H-step blocks after the validation period, and the last block
is the final H observations (for M5, the final 28 days). Standardisation and the
action sets use training data only.

**Metrics** (Section 7.1, Eqs. 15–16) are in `tpo/metrics.py`:
* MSE on the standardised target scale.
* Decision accuracy = share of (window, step) pairs where the forecast induces
  the same optimal action as the realised value.
* Business cost = cost of the action the forecast induces, charged in decision
  units. Costs are normalised per domain and seed so that MSE = 100 before any
  averaging across domains.

## 6. Configuration and seeds

`configs/paper.yaml` holds every setting. Each line is marked `[paper]` (stated
in the manuscript) or `[choice]` (see Section 7).

* **Model seeds:** 42, 123, 456, 789, 2024 (`seeds`).
* **Data seed:** 0. It controls M5 product sampling and synthetic generation.
* **Per-component seeds:** each model within a job draws its own seed from
  (run seed, component name). Results therefore do not depend on job order or
  on how many workers run in parallel.

Runs are deterministic on a given machine and thread count. Across different
CPUs, BLAS libraries or thread counts, floating-point summation order differs.
Expect small numerical differences that average out over seeds, not identical
digits.

Architecture, shared by all neural baselines: 4 layers, 8 heads, d = 256,
feed-forward 1,024, dropout 0.1, 3.29 M parameters (manuscript: "approximately
3.3M"). Training uses AdamW at learning rate 10⁻⁴, batch size 32 and 50 epochs.
T-DPO uses β = 0.1, γ = 0.95, 5,000 pairs, 20 epochs and learning rate 5×10⁻⁵.

## 7. Choices the manuscript does not specify

The manuscript leaves the following implementation details open. Each is fixed
in `configs/paper.yaml` or in the named code, and listed here so it can be
checked:

| Item | Value used | Where |
|---|---|---|
| Epoch length for supervised training (windows are sampled, not enumerated) | 50 mini-batches per epoch | `supervised.steps_per_epoch` |
| Context window length | 96 steps | `context_length` |
| Tokenisation of the context | patches of 16 steps, stride 8 | `architecture.patch_len/stride` |
| Predictive distribution π for DPO | Gaussian per horizon step (mean and variance heads); the variance head is fitted by Gaussian NLL with the mean detached, so the mean stays an MSE fit | `tpo/training.py` |
| Number of candidates per context | K = 8 | `tdpo.num_candidates` |
| Principle parameters | κ = 2, z = 1.96, λ = +1 (upward conservatism), weights w = (0.2, 0.2, 1.0, 0.5) | `constitution` |
| Critical periods c_t (P4) | retail: two weekdays with highest training mean demand; energy: peak hours 10–14h and 18–21h (App. B.1); finance: trailing 21-day volatility above its training 75th percentile | `tpo/data.py` |
| Discrete action set A in Eqs. 15–16 | 21 quantiles of each series' training targets; 11/51/201 reported in `tableS1_action_set_size.csv` | `evaluation.n_actions` |
| Finance cost direction | under-forecast weighted 2× (α⁻ = 2, α⁺ = 1) | `domains.finance` |
| Energy off-peak penalty | under-forecast 1×, peak 10× | `domains.energy` |
| Asymmetric-Loss baseline vs Oracle | Asymmetric: one fixed ratio per domain (energy: 10× at every hour); Oracle: the exact per-step cost (energy: 10× at peak hours only). In retail and finance the two objectives coincide | `tpo/training.py` |
| β selection criterion on the validation set | decision accuracy (Eq. 15); ties → lower validation cost → smaller β | `experiments.beta_selection_metric` |
| Datasets for the β ablation | M5, UCI Energy, Yahoo (the paper reports UCI and says the other two domains behave similarly) | `experiments.beta_datasets` |
| "No principles" ablation | candidates ranked by squared error to the realised target | `tpo/constitution.py` |
| M5 eligibility | products with at least one sale in the training period | `tpo/data.py` |
| Synthetic generators | parameters from App. B.1; noise processes and series counts as in the docstrings | `tpo/data.py` |
